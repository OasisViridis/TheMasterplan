# v5.1.4 发布说明

发布状态以 [GitHub Release](https://github.com/OasisViridis/TheMasterplan/releases/tag/v5.1.4) 与 `v5.1.4` 不可变 Tag 为准；源码版本声明不证明发布已完成。

## 这次改了什么

v5.1.3 之后合入五处修复与一处入口调整：

- 采用计划完整性（[PR #116](https://github.com/OasisViridis/TheMasterplan/pull/116)）：`plan-adopt` 把完整执行器 bundle 写进采用计划，逐文件给出源、所有权与分类；`apply-adopt` 应用前按固定来源、选择项、manifest 与项目当前状态重新核验全部操作，拒绝增删目标、伪造分类与源/目标漂移，本地内容不一致时停在 `LOCAL_MODIFIED`，不再覆盖已有的执行器文件。
- 自身 CI 策略选择（[PR #117](https://github.com/OasisViridis/TheMasterplan/pull/117)）：`themasterplan-check.yml` 改用不可变仓库 ID 判断自身仓库，仓库改名后自身 PR 仍使用当前候选策略，历史 owner 的兼容路径单独保留。
- 授权一致性（[PR #118](https://github.com/OasisViridis/TheMasterplan/pull/118)）：`core/policy.md` 区分日常凭据与获批事务的受限执行能力（§1.2），并补上合并后受约束的派生发布候选（§2.2）。
- 改名后的 `uses:` 引用（[PR #121](https://github.com/OasisViridis/TheMasterplan/pull/121)）：GitHub Actions 不重定向已改名仓库的 reusable workflow，仓库内的自调用改回当前 owner `OasisViridis`。
- 交付入口（[PR #122](https://github.com/OasisViridis/TheMasterplan/pull/122)）：`core/workflow.md` 增加「开工检查」四行表与 §2.1 交付前自检；`AGENTS.md` 要求写第一个文件前确认这四项，交付回复固定四行证据；人类门禁收敛为四类（合并、发布、破坏性清理、数据外发），push 任务分支不再索要授权；`ABSTAINED` 证据只看任务范围的决定。

## 升级时要注意

- 从 v5.1.3 更新会替换受管 Core 规则（`core/workflow.md`、`core/policy.md`）并重写 `AGENTS.md` 受管区块；采纳项目自己维护的项目事实区块不受影响。
- 采用与更新的执行器行为变严：计划不完整、来源或目标漂移、本地 hash 不符时停止写入，不再覆盖既有执行器文件。受管文件不允许本地直接修改；出现 `LOCAL_MODIFIED` 时按停止条件处理，不覆盖项目定制。
- 版本与调用面对齐到 `v5.1.4`：`distribution/manifest.json`、README、中央 Actions 示例与 consumer 模板统一写 `@v5.1.4` 与 `policy-ref: v5.1.4`。不新增 Actions 输入，不改 required check 名称、State schema 或权限，不推进冻结的 `v1`。
- 已发布版本和 `v1` 保持现状，不移动或覆盖。发布采用 tag-only 顺序：annotated Tag → 固定 Tag 消费者 smoke → GitHub Release（`--verify-tag`）→ 远端核验。

## 验证范围与限制

- 仓库回归：`bash scripts/check.sh` 在 Git for Windows Bash 下通过；GitHub Actions 的 PR 检查与 `main` 检查通过。
- 未验证：消费者仓库的真实 `update` / `verify` 运行、固定 Tag 消费者 smoke、多平台采用演练。文档提到的消费者 smoke 仓库 `OasisSaber/TheMasterplan-consumer-smoke` 当前不可达（`gh repo view` 返回 404），本轮没有执行固定 Tag smoke。这些项目不因为本说明、Agent 审阅或 CI 结果而被视为已完成，需要时按采用指南补做。
- 本发布说明不替代所需的人类授权；发布事务按 `core/policy.md` §2 与 `docs/release-channels.md` 执行。
