# 多人协作模式设计

本文记录协作模式访谈中达成的设计结论，整体理解已于 2026-10-10 经人类确认。
规则已在本次工作树中落实，尚待 PR 审阅与人类合并；本文保留设计依据，执行规则以 Core 为准。

## 目标与场景

- 主要场景：两三位人类成员各自使用 Agent，共同维护项目。
- 优先解决：重复实现、互改文件，以及各单元通过但集成失败。
- 以 GitHub 现有功能组织任务认领。

## 已确认的选择

### 执行任务的归属

执行任务以 GitHub Issue 为认领单位，使用 Assignees 记录归属。
尚未认领的执行 Issue 没有 Assignee；认领后只有一位 Assignee。
需要多人并行参与时，将工作拆为分别认领的子 Issue。

父 Issue 的唯一 Assignee 表示当前协调人，子 Issue 的 Assignee 表示各自执行者。
协调人维护父任务的拆分、依赖和整体验收，也可以认领子任务。
汇总父 Issue 由协调人维护，执行任务的自行认领规则应用于实际交付单元。

### 自行认领

对范围已经确认、尚未认领的执行 Issue，成员可以自行把自己设为 Assignee，随后开工。
任务说明包含目标、范围、验收条件和依赖；认领及标签操作使用成员各自的 GitHub 身份与权限。

### 重复认领

同一执行 Issue 出现多位 Assignee 时，双方暂停该 Issue 的写入，保留已有修改。
能明确认领先后时，先认领者保留，另一位退出该任务；无法明确或存在争议时，由当前协调人决定。
归属恢复为唯一负责人后继续工作。先后判断依据可核验的指派记录等事实，不把本地读取到无人认领的时刻当作认领成功。

### 任务准备状态

采用 Matt skills 的默认状态标签词汇：

| 标签 | Issue 中的含义 |
| --- | --- |
| `needs-triage` | 需要团队评估 |
| `needs-info` | 等待报告者补充信息 |
| `ready-for-agent` | 任务已说明完整，适合交由 Agent 实现 |
| `ready-for-human` | 需要人类亲自实现 |
| `wontfix` | 不予处理 |

`bug` 和 `enhancement` 是任务分类，与上述状态分开表达。
Matt 的 triage 约定每个已分类 Issue 具有一个分类和一个状态；本设计沿用该区分。

来源：`setup-matt-pocock-skills/triage-labels.md`、`triage/SKILL.md` 与 `to-tickets/SKILL.md`。
`ready-for-agent` 表达任务准备程度；Matt 的 tickets 即使仍有前置依赖，也使用该标签。

任意团队成员均可自行评估任务，并设置 `ready-for-agent`；该判断由成员基于 Issue 的目标、范围和验收条件作出。
成员的准备状态判断与自行认领仍遵守项目已有的授权和受保护分支限制。

认领与开工筛选条件：Issue 尚未关闭、处于 `ready-for-agent`、没有 Assignee、前置依赖均已满足。
本节记录 Issue 的标签语义，PR 的审阅与合并状态另行设计。

### 不同任务的共享改动

不同执行 Issue 可以并行修改同一文件中的不同部分。
当任务涉及同一接口、类型或逻辑时，先确定一位修改负责人，其余任务依赖该修改的结果。
共享改动优先归入一位负责人的已有执行 Issue，其余任务依赖它；确实需要独立交付时再拆出单独 Issue。

### 依赖记录

使用 GitHub 原生 `Blocked by / Blocking` 关系记录阻塞依赖。
下游 Issue 正文同时说明需要上游交付的具体结果，例如接口字段与行为。
父子 Issue 关系表达工作拆分；阻塞依赖表达执行顺序，两者分别维护。

### 依赖满足与任务交付

上游 PR 已合入 `main`，且下游所需的约定结果验收通过后，才允许下游认领并开工。
固定的未合并候选 SHA 不作为此协作模式下提前开工的依据。
仅关闭上游 Issue 不足以证明依赖满足；取消、拒绝或重复关闭时，需重新核对所需结果及依赖关系。

每个执行 Issue 使用独立工作区、任务分支和 PR，分别合入 `main`。
PR 关联对应执行 Issue；父 Issue 跟踪整体范围与验收。
下游开工时从包含上游已验收结果的基线开始，各单元验收与整体集成验收分别记录。

### 技术审阅与人类批准

执行者自行安排技术审阅，可由 Agent 完成；PR 批准由人类负责。
Agent 技术审阅使用未参与该任务实现的另一个会话，可以由执行者本人发起。
独立性按是否参与候选实现判断；审阅 Agent 读取完整候选 diff、任务要求和验证证据，报告绑定候选 SHA。
任意具备批准资格的非 PR 作者团队成员均可批准 PR，人类结合技术审阅报告、验证结果和风险作出决定。
技术审阅报告与人类批准分别记录；GitHub required approvals、CI 和受保护分支限制继续满足。
候选改动变化后，按新候选重新核验验证、技术审阅及批准状态。
见 [技术审阅与人类批准分离](adr/0001-separate-technical-review-from-human-approval.md)。

本次修改将 Core 的独立技术审阅与人类批准分开；平台正式批准要求仍须满足。

### 整体验收与父任务完成

各子任务交付后，协调人安排 Agent 对合入后的整体结果执行验收，在父 Issue 记录对应基线、验证结果与证据。
全部父任务验收条件满足后关闭父 Issue；子任务全部关闭本身不构成整体验收通过。
集成验收失败时，协调人组织受影响执行者修复并复验，父任务保持未完成。

### 任务释放与接手

成员暂时无法继续时，停止该任务写入，确认会继续写入的相关作业已停止，并留下交接记录，然后清空执行 Issue 的 Assignee，回到待认领队列。
交接记录包括已有修改、基线与候选、分支/PR、验证结果、未完成项、依赖、授权限制及作业状态。
新认领者核验记录与实际状态后继续工作；释放不会自动丢弃已有修改或关闭任务。
成员失联、旧写入作业状态不明或存在冲突时，继续采用现行 Core 的停止与重新指派边界。

## 一条完整任务路径

1. 父 Issue 记录整体目标和验收条件，一位 Assignee 承担协调责任。
2. 拆出可分别交付的执行 Issue，使用 Matt 状态标签和原生阻塞依赖；共享改动明确归属。
3. 成员自行评估准备状态，从未关闭、代理就绪、无人认领且依赖满足的执行任务中认领。
4. 执行者在独立工作区和分支实现、验证，通过关联 PR 提交结果。
5. 未参与实现的独立 Agent 会话技术审阅当前候选，人类结合报告和证据批准 PR。
6. 满足项目合并授权与保护规则后合入 `main`；约定结果验收通过后，下游可以认领并开工。
7. 全部交付完成后，协调人安排整体验收，记录证据并在全部条件满足后关闭父 Issue。

任务释放时从已有候选和交接记录恢复；重复认领时先恢复唯一执行者再继续。

## 已核对的平台行为

- GitHub 的 [Assignees API](https://docs.github.com/en/rest/issues/assignees) 允许向同一 Issue 添加多位受指派人，未提供仅在无人指派时成功的独占认领保证。重复认领通过团队约定处理。
- GitHub 的 [Issue dependencies](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies) 可以表达和显示阻塞关系；依赖关系本身不应被视为自动阻止认领或开工的机制。
