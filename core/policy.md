# Core Policy：授权与发布

> 本文件是 TheMasterplan 工作流中"人类批准"与"发布执行"的权威规则来源。
> 根部 `AGENTS.md` 引用本文件；`profiles/` 下已安装的所选 profile（Git 或 jj）
> 规定具体工具下的安全执行方式。
>
> 权威顺序：本文件不能覆盖系统安全、法律、平台权限、项目安全、隐私、合规、
> 数据保护与受保护分支限制；本文件只定义"人类授权"如何生效、何时失效。

## 1. 授权语义

- 人类保留的是最终决定权，不是必须亲自操作；
- 一次明确授权可以覆盖一组已列明的相关操作（聚合授权）；
- 已批准范围内不重复询问；
- 状态、目标或范围变化时，授权自动失效并重新审核；
- Agent 有工具能力时，不得把已授权操作转交用户手工执行；
- "人工保留操作"表示必须由人类批准，不表示必须由人类亲自操作。

### 1.1 多人授权与冲突

采用项目在根部 `AGENTS.md` 项目事实中定义范围决定者、合并决定者、发布/部署
决定者与代理执行限制；团队身份、协调人指派、PR 作者或普通留言不自动授予审批权。
缺少角色配置或身份无法核实时，停止受影响写入，请求受信任的项目所有者/维护者
提供配置与证据；当前留言者自称有权不构成独立核验。

可核验证据包括受信任会话中的明确人类决定，或由平台读取的 Issue/PR 作者身份
与决定原文，加上项目维护的角色/团队权限配置。仅有复制文本、外部链接、显示名、
任务指派或 CODEOWNERS 文件不证明该人具有 merge/release/deploy 权限；无法读取
真实平台权限时如实报告未核实，不据此执行高权限操作。

授权可以异步记录在 Issue/PR，必须可核验决定者身份与权限、来源、精确目标、候选
SHA（涉及合并/发布时；§2.2 路径在合并前用完整 head/base、预期树及唯一转换
绑定代替尚未产生的结果 SHA，合并后固定并核验结果 SHA）、操作范围和状态。
review approval、任务指派或“请处理”
不自动等于 merge/release/deploy 的批准；多个动作仍可按本文件聚合授权。

矛盾决定、权限不明或有效撤销出现时，停止受影响的写入；不能按“最后一条留言”
或“谁声音大”选择决定。由项目配置的有权人类解决冲突并给出当前有效决定。
转交任务不转移审批权，也不隐式继承对未包含执行身份/操作的旧批准。

独立 review 与执行授权是两道不同的门：审批人也不能凭一句 merge 授权绕过
项目 required reviews、blocking review、CI 或受保护分支限制。候选变化后重新
验证、审阅并审核相关授权；不得修改 GitHub 保护或降低审批人数来解决缺少审阅者。

### 1.2 日常凭据与获批事务的执行能力

日常凭据保持低权限；已批准的 merge/release/deploy 使用人类单独授予、仅能
完成该事务的受限执行凭据。最终审核列明执行身份、日常能力、预期凭据切换、
动作、精确目标及使用期限，清单以 §2.1 为准；凭据值不进入仓库、Issue、PR 或
审核记录。

审核内的预期切换不触发重复批准。执行者分别核验授权有效、实际平台权限足够、
保护门满足；实际权限不足、超出审核列明的动作/目标范围、身份不符或出现审核外
权限变化时停止，不自动扩权或降低 Ruleset。按平台最小可用权限粒度授予能力，
不共享身份或凭据，不授予 admin 或 bypass 能力。事务结束或中止时按审核安排撤销
临时能力并核验其确实失效；撤销失败或无法核验时停止并报告，不把事务报告为完成。

## 2. 聚合授权

聚合授权是指：人类一次批准一组目标明确、顺序明确、范围固定的相关外部操作。
聚合授权不要求对每一个步骤分别确认。

例如，一次发布授权可以同时覆盖：

- 将稳定分支快进到指定 commit；
- 创建指定版本的 annotated tag；
- push 稳定分支和 tag；
- 创建 GitHub Release；
- 验证远端分支、tag（peeled commit SHA）与 Release（tagName）与候选 commit 对齐。

取得聚合授权后，获批的执行者应完成其授权范围内的全部操作，不得对同一范围
重复请求批准，也不得把可由自身工具完成的操作转交人类手工执行。

### 2.1 最终审核必须包含

请求聚合授权（如发布授权）前，最终审核必须列明：

- 发布版本号；
- 候选完整 commit SHA；§2.2 路径在合并前以全部绑定项与唯一派生转换代替结果
  SHA，合并后按 §2.2 固定并核验，不将 PR head 冒充发布结果；
- 目标稳定分支（如适用；tag-only 发布不涉及）；
- 目标 tag；
- Release Notes 状态；
- Release Notes 内容的 SHA-256（对审核列明的最终文件字节计算，不规范化换行；
  派生路径的 Notes 若必须引用合并结果 SHA，改用合并后固定 SHA 的路径）；
- 执行身份、预期凭据切换、动作/目标限制及撤销方式与核验（适用时）；
- 即将执行的全部外部写操作；
- 操作顺序；
- 当前验证结果；
- 当前远端状态；
- 停止条件；
- 已知风险。

缺少关键目标或操作范围时，不得请求发布授权。

Notes 摘要、tag peeled 与 Release 的自动校验必须具备可执行入口与测试；缺少自动
入口时，审核须记录人工核验命令、输出与时间，不得声称自动门已存在或已运行。

### 2.2 合并后受约束的派生发布候选

直接批准既有 `main` 完整 SHA 的 tag-only 路径保持有效。人类也可一次批准
“合并并发布”，但必须显式允许本节的候选转换；单独 PR 批准、merge 授权或
相同内容树都不会自动获得发布授权。该聚合批准必须由同时具备 merge 与
release/deploy 决定权的人类作出；权限分离时分别取得两份可核验决定，不能由
一次审批替代另一种权限。

最终审核除 §2.1 外，绑定仓库、PR、完整 head SHA、审核 base SHA、预期结果
内容树、合并方式（本仓库默认 Squash Merge；审核必须列明，结果提交按该方式
核验父提交）、目标 Tag、Notes SHA-256 和允许的唯一转换：该 PR 按审核方式
合入目标 `main` 后，由平台合并结果派生发布 SHA。预期结果树来自对固定
head/base 的审阅与验证；无法确定时改用合并后单独审核既有 `main` SHA 的路径，
不能用合并后的实际树倒填“预期”结果。

按顺序核验：

1. 合并前重新读取 PR head、目标分支当前 base、有效技术审阅/人类批准、CI 与
   平台保护门，均与审核一致；核验实际执行身份与预期权限切换。
2. 合并后读取平台记录，确认该 PR、目标分支、合并方式及实际合并提交；固定
   结果完整 SHA，核验当前远端 `main` 正好等于该提交，内容树等于已审预期树，
   且父提交结构符合审核列明的合并方式（Squash 时为唯一父提交且等于审核 base）。
3. 对这个固定结果 SHA 重新运行完整验证、审阅转换结果与消费者 smoke；记录
   候选、命令、退出码与证据。全部通过后将其设为 `APPROVED_CANDIDATE_SHA`，
   再进入对应 Profile 的 tag-only 流程；建 Tag 后仍须固定 Tag smoke。针对已审
   预期树的合并结果重验属于受审转换，不触发 §4 的“验证结果失效”。
4. 每次外部写入前复核候选、远端、Tag、Notes 摘要与权限；失败按 §4/§5 停止，
   不自动恢复或沿用已失效授权。

未列明转换、head/base 变化、平台记录不符、额外提交、远端移动、结果树变化、
验证失败、Notes 漂移或权限超出审核均停止重新审核。相同内容树仅是必要条件，
不能允许任意 SHA、任意 `main` 或另一事务复用旧授权。

#### 受约束转换的验收场景

以下是规则正反例，采用演练须另存实际平台与命令证据：

| 输入 | 预期处理 |
| --- | --- |
| 已直接批准现有 main SHA，所有状态和验证仍一致 | 按该固定 SHA 进入 tag-only 发布 |
| 已批准列明 PR/head/base/树/Tag/Notes 的合并并发布；结果与平台记录一致，重验通过 | 接受唯一派生 SHA，继续 Tag 与两阶段 smoke 门 |
| 合并后结果 SHA 上的完整验证与消费者 smoke 全部通过，树/父提交/远端 `main` 与审核一致 | 固定 `APPROVED_CANDIDATE_SHA`，不触发 §4 的验证失效 |
| 合并结果父提交与列明合并方式不符，或 Notes 因引用结果 SHA 而漂移 | 停止，改用合并后固定 SHA 的新审核 |
| 审核列明日常→受限事务凭据切换，身份与实际权限符合限制 | 不重复批准，核验保护门后执行 |
| 只有 PR 批准或 merge 授权，未列明发布与候选转换 | 不推导发布授权，单独准备最终审核 |
| head/base 变化、额外提交或 main 已移动；即使树相同 | 停止，不复用原授权 |
| 实际结果树与预期不同，或完整验证/任一 smoke 未执行或失败 | 停止，不建 Release |
| 身份不符、权限不足、审核外权限切换或平台门未满足 | 停止，不扩权或绕过保护 |
| Notes 摘要或 Tag 变化，或部分发布成功后出现错误 | 停止，核验已完成状态再重新审核恢复 |

## 3. 发布事务

发布采用单一最终授权门，完整流程：

```text
只读检查与准备
→ 最终发布审核
→ 人类一次批准
→ 连续执行发布事务
→ 远端验证
→ 最终汇报
```

不得拆成逐步确认（推进分支 → 创建 tag → push → 创建 Release 各确认一次）。

### 3.1 阶段 A：自主准备

在产生发布性远端写入前，当前发布执行者自行完成：

- fetch 最新远端状态；
- 确认候选 commit；
- 确认版本号；
- 检查目标分支；
- 检查目标 tag 是否已存在；
- 检查目标 Release 是否已存在；
- 运行完整验证；
- 阅读完整 diff；
- 检查 changelog；
- 生成或整理 Release Notes；
- 检查稳定分支是否可快进（如适用；tag-only 发布不涉及）；
- 检查是否存在冲突；
- 准备精确命令或 API 操作；
- 汇总风险和停止条件。

这一阶段属于准备和只读检查，不应要求用户逐步参与。

### 3.2 阶段 B：最终发布审核

向人类提交一次完整审核，包含 2.1 列明的全部要素，并给出"批准或拒绝本次
完整发布事务"的唯一决定点。用户只需回答一次（如"批准发布"）。

### 3.3 阶段 C：连续执行

获得批准后，连续执行已列明步骤。在授权范围和远端状态未变化时：

- 不得重复请求批准；
- 不得要求用户手工运行命令；
- 不得把"人类最终决定权"解释为"人类必须亲自操作"；
- 不得在每一步之间暂停等待无必要确认。

### 3.4 阶段 D：发布后验证

验证：

- 稳定分支指向预期 commit（如适用；tag-only 发布不涉及）；
- tag 指向预期 commit；
- GitHub Release 使用正确 tag；
- Release Notes 正确；
- 不存在意外分支、tag 或额外修改；
- CI 或发布后检查状态符合预期。

然后一次性汇报已执行操作、最终 commit、分支、tag、Release、验证结果与
任何异常或残留风险。

## 4. 聚合授权失效条件

出现以下任一情况时，必须停止，并重新提交最终审核：

- 候选 commit SHA 发生变化（仅 §2.2 明确审核并完成全部核验的唯一派生转换例外）；
- 版本号发生变化；
- 目标分支发生变化；
- 目标 tag 发生变化；
- Release Notes 内容摘要发生变化；
- 验证结果失效（§2.2 第 3 步对已审预期树合并结果的重验属于受审转换，不触发本条）；
- 远端 main/目标稳定分支在授权后被修改（§2.2 的唯一受审合并转换除外；tag-only 也核验 main）；
- 目标 tag 或 Release 在授权后被创建；
- 出现冲突；
- 操作范围扩大；
- 需要强推；
- 需要覆盖或删除现有 tag；
- 需要删除远端资源（§7.1 已合并任务分支清理豁免除外）；
- 需要执行审核中未列出的操作；
- 部分操作成功后，继续执行可能造成不一致；
- 审核外工具权限或平台能力发生变化；§1.2 已列明且经核验的预期切换不重复批准。

重新审核时必须说明：已完成哪些步骤、未完成哪些步骤、当前远端状态、
是否需要回滚、新的风险、新的完整操作计划。

## 5. 部分失败处理

### 5.1 不得盲目重试

发布事务中途失败时：

- 不得自动重复创建 tag；
- 不得盲目重复 push；
- 不得盲目重复创建 Release；
- 不得用强推掩盖状态差异；
- 不得猜测哪一步已经成功。

### 5.2 必须先核验状态

检查：

- 稳定分支当前指向；
- tag 是否已创建；
- tag 是否已推送；
- GitHub Release 是否已存在；
- Release 是否关联正确 tag；
- 是否有部分成功状态。

### 5.3 重新授权边界

如果恢复需要删除 tag、覆盖 tag、强推、删除 Release、修改已发布 Release、
改变版本号或改变候选 commit，则必须重新取得人类授权。

## 6. 术语对照

| 旧表述 | 新含义 |
|---|---|
| 人工保留操作 | 必须由人类批准 |
| Agent 不得 release | 未经批准不得 release |
| 人类推进稳定分支 | 人类决定是否推进，Agent 获批后可执行 |
| 单独明确授权 | 可以是一次覆盖完整事务的明确授权 |
| 需要人类执行 | 只有工具确实无法完成时才由人类操作 |

## 7. 边界（聚合授权不是无限授权）

聚合授权仍然是：对精确目标、精确范围和精确状态的一次性授权。它不意味着：

- Agent 可以未经批准发布；
- Agent 可以自动选择版本号并发布；
- Agent 可以强推；
- Agent 可以未经针对该历史的明确授权重写已 push 的任务历史（包括
  restack/rebase 后移动已发布的任务分支或 bookmark）；
- Agent 可以覆盖现有 tag；
- Agent 可以删除 Release 或远端资源；
- Agent 可以忽略验证失败；
- Agent 可以把 §2.2 的受约束转换推广为任意候选 SHA 变化仍继续使用旧授权；
- Agent 可以把"最高权限"理解为无限授权。

### 7.1 唯一豁免：已合并任务分支清理（PR 生命周期收尾）

已合并任务分支的远端删除是 PR 生命周期的标准收尾步骤，不属于上述
「删除远端资源」边界。当且仅当满足以下全部条件时，Agent 可在合并后
直接删除远端任务分支并清理本地同名任务引用（Git 分支或 jj bookmark），
无需另行授权：

1. 该分支由 Agent 为本次任务创建（短生命周期任务分支，jj 下为 bookmark，
   `core/workflow.md` §3），且非受保护分支；
2. 分支引入的全部变更已进入默认分支：对应 Pull Request 已合并（状态
   MERGED、目标分支为默认分支），或已由人类确认分支的全部变更已合入；
3. 没有打开的 Pull Request 引用该分支；
4. 不涉及 tag、Release、他人分支或强推；
5. 删除前先执行 dry-run（Git：`git push --dry-run --delete <remote> <branch>`；
   jj：`jj git push --deleted --dry-run`）确认无目标以外的待删除 ref；删除后
   以 `git ls-remote` 验证 ref 消失，并在交接中记录。

任一条件不满足即回到逐次授权路径。本豁免不扩展至 tag、Release、他人
分支、未合并分支或受保护分支的任何删除。

## 8. 工具不可执行时的最小人工操作

当前平台无法完成已批准事务中的某个步骤（如无法创建 GitHub Release）时：

- 完成所有能够完成的准备与已批准操作；
- 明确指出唯一无法执行的步骤及其原因；
- 提供该步骤的最小人工操作命令；
- 不把整个发布流程都转交给用户。

## 9. 最终原则

> 人类决定是否发布，Agent 负责执行已批准的发布事务。

> 发布前集中审核一次，发布中不重复打断。

> 已批准范围内不重复询问，状态或范围变化时重新询问。

> 人工保留操作表示必须由人类批准，不表示必须由人类亲自操作。

> 安全来自精确目标、完整验证和状态变化检测，而不是来自无休止的重复确认。
