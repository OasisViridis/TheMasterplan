# Core Workflow：任务与交付

> 本文件只定义日常任务治理。权限、发布和破坏性外部操作按需读取
> `core/policy.md`；工具命令按 Context Router 读取对应参考，不在这里复制。

## 0. 治理所有权

TheMasterplan 只在自己是当前任务的交付治理所有者时工作。治理所有权属于协议，
不等于一位成员永久拥有任务。多人按同一协议分工或交接不触发退让。

直接使用编辑器、Shell、Git/jj、OpenCode、Codex、ChatGPT、测试或构建工具本身
不构成冲突。若当前上下文明确表明另一个系统已经拥有 worker/session、任务
workspace/worktree/branch、Issue→PR 状态机、CI/review 路由或
merge/release/deploy 生命周期，则：

```text
TheMasterplan: ABSTAINED — external delivery workflow owns this task.
```

`ABSTAINED` 是任务级瞬时状态，不写入 `.themasterplan/state.json`。不要按品牌、
目录名或版本猜测外部所有权，也不要为外部 orchestrator 建兼容层。

## 1. 任务与范围

- 复杂任务：使用 Issue 记录目标、范围、验收条件与排除项。
- 小型低风险任务：可以使用当前会话中的明确人类授权；PR 记录授权来源、目标、
  范围。
- 微小修复快速通道：仅限目标清晰、无范围争议、单文件或极少数同主题文件、
  约 ≤30 行、只涉及文档/配置/测试/注释、不触及核心逻辑或公共接口、不涉及
  持久化数据/部署/发布/远端数据/破坏性操作，并且验证与最终 diff 均正常。
  需要针对该修复的会话内明确授权；不满足任一条件就走普通 PR 路径。
- 无 Issue 时不得伪造编号。
- 实现需要实质扩大范围时，停止并请求新的范围决定。
- 授权可以来自可核验的 Issue/PR 人类决定或当前会话，不必与执行者在同一会话；
  记录来源、决定者、目标与范围。留言、指派和 review 不自动等于执行授权。

### 1.1 团队角色

在任务记录中标明模式（单人/团队）和当前角色，不按账号共享所有权：

| 角色 | 责任与边界 |
| --- | --- |
| 协调人 | 父 Issue 的唯一 Assignee，维护拆分、范围、依赖、状态与整体验收；也可认领子任务 |
| 执行者 | 执行 Issue 的唯一 Assignee，拥有该单元的 worktree、任务 ref 和 PR；按授权提交/push/PR |
| 独立技术审阅者 | 团队任务至少一位未参与候选实现的参与者，复核完整 diff、任务要求、验证与风险；可以是 Agent |
| PR 批准人 | 具备项目批准资格的人类成员，结合技术审阅、验证与风险批准候选；不由协调人垄断 |
| 人类决策者 | 按项目角色配置决定范围、merge、release/deploy；协调或执行身份不自动授予此权限 |

单人可以兼任协调与执行；协调人未参与实现时可以兼任技术审阅者。执行者自行
安排技术审阅；审阅 Agent 使用未参与该候选实现的另一个会话，可以由执行者
本人发起。独立性按实现参与情况判断，主代理自审或参与实现的子代理不算独立
技术审阅。Contributors 列出全部实际实现者，包括实现 Agent 的稳定会话标识；
Reviewer 使用审阅人或审阅 Agent 会话的稳定标识，不能漏记实现者伪造独立性。

技术审阅与人类 PR 批准分别记录；Agent 技术审阅不能充当人类批准或合并授权。
即使平台 required approval 数量为零，团队 PR 仍须具备批准资格的人类
批准；不能降低或绕过项目更严格的 CI、CODEOWNERS 或受保护分支要求。
模式以任务授权/Issue 为准，不通过把团队 PR 改标 solo 绕过审阅；模式转换需
有权范围决定者确认，既有审阅义务不被抹除。
各执行者维护自己的任务 ref，不需要一个人代所有人操作 VCS。一个 Agent 会话
内部仍由主代理负责该会话的外部写入；子代理不独立执行外部交付写操作。

### 1.2 Issue 准备与认领

父 Issue 汇总目标与验收，由一位 Assignee 协调；执行 Issue 是可独立验收和认领
的交付单元。需要多人并行时拆为子 Issue，各自认领；父子关系只表达拆分。
无拆分的任务直接使用执行 Issue，执行者兼任协调人。

使用 Matt 的默认状态标签；`bug` / `enhancement` 表示分类，与状态分开。
已分类的执行 Issue 使用一个分类和一个状态；切换状态时移除旧状态标签。

| 状态 | 含义 |
| --- | --- |
| `needs-triage` | 需要团队评估 |
| `needs-info` | 等待报告者补充信息 |
| `ready-for-agent` | 目标、范围、验收条件和依赖说明完整，适合 Agent 实现 |
| `ready-for-human` | 需要人类亲自实现 |
| `wontfix` | 不予处理 |

任意有相应平台权限的团队成员均可评估并设置 `ready-for-agent`。它只表示准备
程度，不证明依赖满足、无人认领或执行授权。认领前核验：执行 Issue 未关闭、
处于 `ready-for-agent`、没有 Assignee、全部前置依赖满足，且工作在已授权范围。
成员使用自己的 GitHub 身份将自己设为唯一 Assignee，重新读取实际指派结果，
确认仍符合条件后开工，不要求协调人逐次批准正常认领。

GitHub Assignees 不是独占锁：添加会保留已有 Assignee，不保证“仅无人认领时
成功”。出现多位 Assignee 时，各方暂停该 Issue 写入并保留修改；可核验指派
记录明确先后时由先认领者保留，其他人退出；无法判定或存在争议时由协调人
解决。恢复唯一 Assignee 并核对作业状态后继续；本地读取空名单不证明认领成功。

### 1.3 并行、依赖与整体验收

- 每个执行 Issue 使用独立 worktree、任务分支和关联 PR，分别合入 `main`；
  记录文件边界与基线，不默认使用共享集成分支或未合并上游的 stacked PR。
- 同一执行 Issue/任务 ref 同时只有一个写入者。不同 Issue 可以并行修改同一
  文件的不同部分；涉及同一接口、类型或逻辑时，先确定一位修改负责人。
  共享改动优先归入其已有执行 Issue，确需独立交付时再另建 Issue，其余任务
  依赖该结果；不覆盖他人修改或抢占 ref。
- 使用 GitHub 原生 `Blocked by / Blocking` 记录阻塞关系，下游正文说明所需
  的具体结果；父子关系不能代替阻塞关系。平台显示的阻塞状态不是自动开工门。
- 上游 PR 已合入 `main` 且约定结果验收通过，才算依赖满足，才允许下游认领
  开工。正文记录合并提交、验收结果与证据；关闭 Issue 或审阅过的未合并 SHA
  均不足以证明满足。取消、拒绝、重复关闭时重新核对结果和依赖，不能自动开工。
  下游使用包含已验收上游结果的 `main` 基线；上游结果失效时复核并暂停受影响工作。
- 各单元通过不等于集成通过。全部子任务交付后，协调人安排 Agent 对合入后的
  整体结果运行权威检查并验收跨单元行为，在父 Issue 记录完整基线、结果与证据。
  全部父任务条件满足后才关闭；失败时组织受影响执行者修复和复验，父任务保持
  未完成。子任务全部关闭不替代整体验收。
- 团队任务走普通 PR，不能用微小修复快速通道绕过技术审阅、批准或保护规则。

### 1.4 任务释放与责任交接

交接记录保存在任务 Issue/PR，不写入采用版本的 `.themasterplan/state.json`。
必须包括交付单元与写入者、完整基线/候选 SHA、worktree/ref/PR、现有修改、
验证命令与结果、未完成项/依赖、授权来源/限制和作业状态；协调权交接另记
旧/新协调人。

正常释放执行任务时，原执行者停止该任务写入，核验会继续写入的相关作业已
停止，留下交接记录，再清空执行 Issue 的 Assignee，交回待认领队列。释放不
丢弃修改、不关闭任务、不证明就绪或依赖满足。新认领者按 §1.2 筛选，核验
记录与实际文件、diff、远端和作业状态后继续；无需提前指定下一位执行者。

新协调人核验实际文件、diff、远端与作业状态，明确接受；旧协调人确认停止该任务
写入后协调权交接生效，并同步父 Issue 的唯一 Assignee。原负责人不可用、旧
作业状态不明时，只能由有权人类明确重新指派，核实旧作业已停止或隔离后接手。
日志、意图或一次观察超时不证明作业已经停止。

未接受/未核验前不宣称完成交接；存在两位活跃写入者、未知修改、冲突 ref 或
互相矛盾的决定时停止有风险写入，保留状态并按 Policy 请求有权人类决定。
交接不是授权升级；需要改变执行身份、目标或操作范围时重新审核授权。

## 2. 默认继续与完成

识别到知识或方法缺口、关键不确定性时，立即按
`core/skill-collaboration.md` 选择适合且已可用的方法技能主动求助，无需先失败。
没有相关缺口的简单任务直接完成；求助后仍按当前授权与完成合同继续交付。

在授权范围内，默认继续完成安全的本地工作：

```text
读取相关文件
实现/编辑
格式化、lint、测试
修复本次改动造成的失败
重跑受影响验证
检查工作区与最终 diff
准备交付材料
```

不要在第一次实现后仅因为“可以让人审阅”而提前结束；以根部 `AGENTS.md`
Completion Contract 为完成定义。

## 3. 工作区、验证与 diff

- 开始写入前确认任务来源、工作区归属和未知本地修改；不覆盖来源不明的修改。
- 一个交付单元对应一个可验证 change/短生命周期任务引用；并行子任务各自隔离，
  父任务记录集成依赖，不混入无关修改。
- 迭代中按改动风险运行受影响验证：文档检查链接与契约，行为修改运行相关测试；
  无法界定影响、跨模块或共享接口改动时扩大验证。无需每次编辑重跑全套。
- 先确认命令的副作用；未知验证入口不等于安全本地测试。涉及真实数据、生产服务、
  部署或远端写入的验证仍遵守项目安全与授权边界。
- push 前对最终候选运行根部 `AGENTS.md` 记录的完整权威验证入口，并阅读完整最终
  diff。相关测试不能代替这道门；修改使验证失效时必须复验。
- 验证失败时，修复由本次改动造成的问题并重跑相关验证；不得把失败或未执行
  的验证表述为通过。
- 基线、任务引用或远端 ref 冲突且正确目标不明确时停止，不猜测、不强推。

## 4. Pull Request 交付

普通 PR 使用仓库 `.github/pull_request_template.md`，让模板与 CI validator
作为机械契约的单一事实来源；不要在 Skill 或其他入口复制字段清单。

PR 必须提供通俗易懂的中文修改简报；填写方式以 PR 模板为准。

创建或更新 PR 后：

- 等待关联 CI；
- CI 因本次修改失败时继续修复并重跑；
- 团队 PR 记录协调人、执行者、独立审阅者、依赖与当前候选；按模板维护协作记录；
- 独立技术审阅绑定候选 SHA，修改后的候选不得沿用旧审阅；blocking review 未解决时
  不报告可合并，不自行 dismiss 别人的意见；
- CI 通过可以报告验证通过；团队 PR 技术审阅完成后提交有资格的人类批准。
  单独记录受信任会话中的人类批准；项目要求原生 review 时，从平台核验
  批准人、状态与 commit。正文
  结构、自审勾选或 Agent 报告不能证明批准。候选变化后重新核验批准有效性，
  即使平台未自动 dismiss 旧批准也不把它当作新候选已批准；
- 完整检查、适用的独立技术审阅与人类 PR 批准、项目保护门满足后，再由有权人类决定
  是否合并；PR 批准不自动等于 merge/release/deploy 授权；
- 合并后的 Agent 自建任务分支按 `core/policy.md` §7.1 处理清理。

## 5. 真正的停止边界

以下情况才需要停止并取得人类决定或重新授权：

- 安全、隐私、合规、Secret 或数据风险；
- 任务范围发生实质扩大；
- merge/release/deploy/受保护分支推进缺少所需授权；
- 需要强推、移动/覆盖已发布 Tag、覆盖未知人工修改；
- 远端 ref、候选 SHA 或已批准状态发生冲突/变化；
- 外部交付工作流已拥有当前任务；
- 继续操作将跨越 `core/policy.md` 定义的破坏性或发布边界。

## 6. 卫生与审查

最终 diff 不应包含误删、范围外变更、调试代码、临时文件、缓存或无关生成物。

代码审查意见只使用三类：

```text
合并前必须修复
建议本次修复
可以后续处理
```

每条意见说明具体问题、影响和需要的修复。
